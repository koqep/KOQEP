# ADR-0002: Token-based API auth, not Next.js session cookies

**Date:** 2026-07-28
**Status:** Accepted

## Context
*Mobil uygulama 6+ ay sonra geliyor ama backend'in baştan mobil-uyumlu olması gerekiyor; oturum yönetimi Next.js'e bağlı olursa mobil istemci session cookie'lerini tüketemez.*

Native mobile is planned as a v2+ effort (6+ months out per the founder), but the API must not require a rewrite when that client arrives. If session state lived only in Next.js (server-set cookies), a native app would have no natural way to consume it, and adding token auth later would mean touching every authenticated route and re-issuing every session flow.

## Decision
The backend NestJS service issues short-lived access tokens and longer-lived refresh tokens on login/signup. Next.js is treated as just the first API consumer — it stores tokens (e.g., in an httpOnly cookie for the web client specifically, but the *API* itself is cookie-agnostic) and calls the same token-authenticated endpoints any future mobile client will call. No business logic or session authority lives in Next.js.

## Alternatives considered
- **Next.js-owned session cookies** — rejected: blocks mobile by construction; a native client can't send browser-scoped cookies, forcing a full auth rewrite at mobile launch.
- **Third-party auth-as-a-service (Auth0, Clerk, etc.)** — rejected: recurring cost and vendor lock-in not justified at $50/mo budget and 600-user scale; token issuance is not a hard problem at this size.

## Consequences
- Positive: mobile client, when built, is a new consumer of an already-mobile-ready API — no backend rewrite.
- Cost / risk accepted: slightly more auth code upfront (token issuance, refresh, revocation) than "just use Next.js sessions" would require.
- Cost to reverse later: high if deferred — reversing this after mobile ships means migrating every authenticated session and client simultaneously. Cheap to get right now; expensive to retrofit.

## Addendum (2026-08-14, M7a Slice A — finishing the "httpOnly cookie" mechanism)
*Bu kararın "web istemcisi token'ları httpOnly cookie'de saklar" cümlesi hiç uygulanmamıştı — `apps/web/app/page.tsx` sadece bellek-içi React state kullanıyordu, kendi yorumunda bunu "ara adım" diye tanımlıyordu. Bu bölüm o mekanizmanın gerçek tasarımını (ve kararlaştırılmamış CSRF/çoklu-sekme sonuçlarını) belgeler.*

**Only the refresh token moves to a cookie, not the access token.** The Decision line above is deliberately hedged ("e.g., in an httpOnly cookie") rather than mandating both tokens move — this addendum resolves that ambiguity narrowly, in the direction closest to the ADR's own stated goal (API stays cookie-agnostic): the access token (15-minute TTL) continues to travel as `Authorization: Bearer` on every request, unchanged from day one; only the refresh token (30-day TTL, the higher-value artifact) moves into an `httpOnly; Secure; SameSite=None; Path=/auth` cookie (`koqep_rt`), paired with a second, JS-readable `Path=/` cookie (`koqep_csrf`) used for double-submit CSRF verification. This was chosen over moving both tokens to cookies for concrete reasons found by reading the actual code, not by assumption:
- `apps/api/src/api/jwt-auth.guard.ts` is the single chokepoint for every guarded route (15+ endpoints) and reads *only* the bearer header — leaving the access token there means this file, and every route it guards, needed zero changes.
- `apps/api/src/api/messages.gateway.ts`'s WebSocket handshake auth reads `handshake.auth.token`, an explicit value the client constructs — an httpOnly cookie can't populate that by design, so a full-cookie design would have required teaching the gateway to parse cookies off the raw handshake headers. Leaving the access token in memory means the gateway needed zero changes.
- CSRF exposure narrows to exactly two endpoints (`/auth/refresh`, `/auth/logout` — the only two that read the httpOnly cookie) instead of every state-changing route in the API, since bearer-header auth is not itself forgeable by a CSRF page.
- `apps/web`'s ~9 components that thread `accessToken` as a prop needed no changes; only the now-unused `refreshToken` prop was removed.

**CSRF defense: double-submit cookie, not a synchronizer token.** `koqep_csrf` is set alongside `koqep_rt` on every login/refresh, and the web client echoes its value back as an `X-Csrf-Token` header on `/auth/refresh`/`/auth/logout` calls; the server rejects (403) if the header is missing or doesn't match the cookie. This requires no server-side session storage beyond what already exists, and no new dependency (`csurf` was considered and rejected — it's unmaintained upstream, and the check itself is a few lines of cookie-parsing, not enough surface to justify a package). `apps/api/src/services/auth-cookie.util.ts` holds the cookie-building/parsing helpers; the CSRF check lives inline in `AuthController` since it's two call sites, not a cross-cutting concern.

**Multi-tab refresh-token rotation race — accepted, time-boxed grace period.** Refresh-token rotation (already in place before this addendum) revokes the old token the instant a new one is issued. Two browser tabs sharing the same httpOnly cookie can race: tab A rotates, tab B's already-in-flight request (built from the pre-rotation cookie value) then presents an already-revoked token and would, without mitigation, log a still-valid user out. `apps/api/src/services/auth.service.ts`'s `refresh()` now tolerates reuse of a *rotation-revoked* token for a **10-second window, exactly once** (`RefreshToken.graceReusedAt`, `REFRESH_TOKEN_REUSE_GRACE_MS`) — a named, industry-standard pattern ("refresh token reuse detection with grace period"), not an ad hoc weakening. Two things keep this narrow: the grace claim is atomic (`updateMany` with a `graceReusedAt: null` guard, so two racing grace attempts can't both succeed) and it is granted **only** when `RefreshToken.revokedByRotation` is `true` — a token revoked by an explicit `logout()` or by `confirmPasswordReset()`'s bulk session-kill never gets a grace window, so "I clicked logout" always means immediate, unconditional termination. This distinction was added after the deliberate-logout case was found to inherit the grace tolerance by accident during implementation; it is now covered by a dedicated regression test (`reddeder_logoutla_iptal_edilmis_tokeni_grace_penceresi_icinde_bile`).

**A second, unrelated bug found and fixed in the same slice: 401 is not a reliable "token expired" signal.** The web client's new silent-refresh-on-401 retry (`apps/web/lib/api.ts`) initially retried on any `status === 401` from an authenticated call — but several domain rules in this codebase (wrong TOTP code, wrong password during account deletion) *also* return 401 from already-guarded routes, and are indistinguishable from a truly expired token by status code alone. A blanket retry silently replaced those real, user-facing error messages with a generic "session could not be refreshed" failure (caught by this slice's own Playwright suite, not by manual testing). The fix: only the code paths that mean "the access token itself is invalid" (`JwtAuthGuard`'s missing-header check, `AuthService.verifyAccessToken`'s failure, and the two "token verified but the account behind it is gone" cases in `deleteAccount`/`UsersService.getProfile`) now carry a structured `code: 'INVALID_TOKEN'`; the frontend retries only on that exact code, never on bare 401.
