# KOQEP — Threat Model

*Her satır: aktör → hedef → saldırı yolu → kontrol → kalan risk. Phase 1'in güvenlik bulgularının somut kontrollere dönüştürülmüş hali.*

| # | Actor | Goal | Attack path | Control | Residual risk |
|---|---|---|---|---|---|
| 1 | Sybil operator | Mass fake accounts to manipulate reputation/invites | Use own invite tree to farm accounts, low-effort messages to earn XP → more invites | **Revised M4 Slice B (2026-08-04):** manual invite issuance (and its explicit 5/hour-per-user rate limit, shipped M2 Slice C) was removed entirely — invites are now earned only automatically, 1 per level-up. The real ceiling today is indirect, derived from the WS message-send rate limit (10 msgs/10s, `messages.gateway.ts`) × `MESSAGE_SENT_XP=1` ÷ `XP_PER_LEVEL=35` ≈ **~100 invites/hour/user, theoretical max** — about 20x looser than the removed explicit cap. ReputationEvent log (ADR-0004) still makes farming patterns auditable | The new ceiling is real but far more permissive than the control it replaced, and reaching it requires sustained max-rate messaging (unrealistic for a genuine user, plausible for a scripted one) — a determined sybil operator has meaningfully more room than before. Small community still makes patient farming more likely to be noticed by other users |
| 2 | External attacker | Account takeover | Credential stuffing / reused passwords; TOTP is optional so many accounts are single-factor | argon2id/bcrypt password hashing; TOTP optional but encouraged, with recovery codes at setup; refresh-token rotation/revocation | Accounts that decline TOTP remain single-factor — accepted tradeoff from Phase 1 (mandatory TOTP was a bigger risk: solo-founder lockout support burden) |
| 3 | Compromised or malicious account holder | Post benign content, edit into abuse after reputation accrues | Edit a message post-hoc once trust/level is established | MessageEdit history retained; **visible only to the message's author and to moderators** — resolved this phase, not public (avoids edit history becoming a harassment/surveillance tool) | Moderator response time is bounded by a solo operator's availability — no 24/7 coverage |
| 4 | Any authenticated user | XSS / content injection | Malicious markdown/HTML payload in a message | Rendered markdown passes through a sanitizing allowlist; strict CSP, no inline scripts, no remote script sources | Sanitizer or renderer library CVEs — mitigated by dependency updates, not eliminated |
| 5 | Any user or bot | Flood a room / degrade availability | Automated rapid message sending | Rate limits at the WS gateway: per-user, per-IP, per-connection — **not implemented today; planned for M2 Slice C** (a custom WS guard extending `ThrottlerGuard`) | Message sending is fully unthrottled until Slice C ships. Even once it exists, a determined actor with many accounts (ties to #1) can still degrade one room temporarily |
| 6 | Malicious user | Room-spam / squat the browse list, waste storage | Rapid, repeated room creation | Room creation capped at 1/user/24h; 14-day auto-archive removes dead rooms from the active list (ADR-0006) — **not implemented; deferred to M3**, not M2. Tied to user-created rooms, which don't exist until M3 — nothing to cap or archive today. Core rooms #general/#meta (M2) are exempt by design once they exist, not because any exemption code runs | A creation burst is still visible for up to 14 days before archiving, once M3 builds this |
| 7 | Coordinated group | Brigading — flood a room or harass a target using invite-tree access | Multiple invited accounts act in concert, controlled or coordinated by one actor | Invite-issuance control same as row 1 — **M4 Slice B (2026-08-04):** explicit rate limit replaced by the indirect, ~20x looser WS-message-derived ceiling (see row 1); reputation stays an honest signal (Boost-for-XP already killed, Phase 1); moderation is transparent temp-mute, not shadow ban, so bad actors can be muted openly and fast | Small community size means even a handful of coordinated accounts have real impact; best mitigation is a shallow invite tree and an attentive solo moderator, not technical controls alone |
| 8 | Regulator / legal claimant | Platform found non-compliant (KVKK/GDPR/5651) | N/A — this is a compliance gap, not an attack | Log retention policy + documented takedown process (Phase 1); anonymize-on-delete instead of hard-delete (ADR-0005) | Turkey-specific case law on anonymization-as-erasure is not yet legally verified — flagged from ADR-0005, needs a cheap legal check before real traffic |
| 9 | Unauthenticated actor | Guess a valid invite code | Brute-force / enumeration attempts | Single-use — **implemented and tested** (`usedAt`/`usedById`). High-entropy — **not enforced by any code today**: every `Invite.code` ever created (M1's now-removed `DEV_INVITE_CODES` seed constants, and the manually-SQL'd production bootstrap invite) was a human-chosen string, not server-generated; M2 Slice C's server-side generator is the first thing that will actually guarantee entropy. Rate-limited attempts — **not implemented, planned for M2 Slice C** (retrofit `POST /auth/signup`) | Until M2 Slice C ships, an invite code's real strength depends entirely on whoever typed it when creating the row, and guessing attempts are unthrottled. Low once Slice C lands — standard token-guessing risk at that entropy level |
| 10 | Abusive account holder | Harass another user via DM, where room moderation doesn't reach | Send abusive content 1:1; no other user or moderator witnesses it | **Row written as if DM exists — it doesn't (confirmed 2026-07-30, no `Conversation`/`DirectMessage` model anywhere in the schema). Deliberately deferred past 1.0, see `docs/BACKLOG.md`'s "2026-07-30 — LANSMAN KARARI": a 20-30 person closed cohort already talking visibly in 2 shared rooms doesn't need DM's absence to feel broken or unsafe.** The controls below describe the intended design for whenever DM ships, not a current mitigation: DMs are not proactively scanned. A report on a DM message exposes only that reported content to a moderator for review (report-triggered visibility, not ambient surveillance — same model Discord/Slack use). Block/mute stops further contact immediately, independent of any report. Additional signal: if the same account is blocked/reported by multiple distinct users within a short window, auto-flag for moderator attention | Requires the victim to report — a victim who doesn't report leaves no trail; pattern-detection across reports is a weak, not a strong, backstop. **Until DM ships, this entire row's risk is moot — row kept for design continuity, not as an active gap.** |
| 11 | External attacker with a compromised email account | Take over a KOQEP account via password reset | Request password reset, receive the link via the compromised email, set a new password | If TOTP is enabled, resetting the password alone is not sufficient — TOTP is still required to log in. Reset links are single-use and short-TTL; a reset event sends a notification to the account's registered email; all active sessions/refresh tokens are revoked on password change, forcing re-auth everywhere | For accounts without TOTP (optional per Phase 1/ADR trade-off), email compromise is account compromise — the notification is after-the-fact, not preventive. This is the direct, accepted cost of making TOTP optional; stated plainly, not hidden |
| 12 | Moderator (insider) | Misuse standing access to edit history or reported content | Browse MessageEdit history or reported DM content without an actual open report/investigation reason | Moderator access to a message's edit history is scoped to an active report on that specific message/user — not a general "browse anything" query. Every moderator access and every moderation action (mute/ban) is written to its own append-only audit log (same pattern as ReputationEvent, ADR-0004): who, what, on whom, when | With a single solo moderator (the founder) at this stage, there is no independent, real-time oversight — the audit log gives after-the-fact accountability only, not prevention. Honest residual risk of a solo-operator platform, not solved by tooling alone |
| 13 | Anyone with read access to the private repo (collaborator, leaked credential, compromised device) | Bypass invite-gating entirely; self-register on production, or log into a live account, with zero real credential | `apps/api/src/db/dev-seed.constants.ts` holds `DEV_INVITE_CODES` and `DEV_USER_EMAIL`/`DEV_USER_PASSWORD` in plaintext, committed to git; every deploy's `preDeployCommand` (`db:seed`) previously wrote both the invite codes and a real, real-password-hash dev account into the **production** database, unconditionally | `apps/api/src/db/seed.ts` now gates dev-user + invite-code creation behind an opt-in `SEED_DEV_FIXTURES` env var, default OFF (verified: `db:seed` with the var unset creates only the room, nothing account/invite-related). Production's existing dev-user row and any account signed up via a `DEV-INVITE-*` code were manually deleted from the live DB (2026-07-29) | Repo is currently private, so no external leak today — but this was the exact same risk class as the closed row 13 dev-login bypass (a "dev convenience" fixture that was a real, standing production access path). No real "issue an invite" endpoint exists yet; founder-issued invites are manual `Invite` table inserts via the Render Postgres console until one is built (M2+) — a real gap, tracked in Open items, not silently accepted |

**Closed (M1 Slice E5, formerly row 13):** previously tracked `POST /auth/dev-login`,
an M0 stopgap that issued a real token with zero credentials for the seeded dev user,
gated only by `ENABLE_DEV_LOGIN`. `DevAuthController`, the env-gate, and every remaining
reference were deleted entirely — there's no longer a route or a flag to re-enable by
accident, so this is a closed row, not just a mitigated one. Removed from the table
(its number was later reused above for a different, still-open finding — the two are
unrelated beyond both originating from the same `dev-seed.constants.ts` file).

## Open items carried forward
*Bu modelde çözülmeyen sekiz şey: TR'ye özgü hukuki doğrulama, tek moderatörlü denetim boşluğu, TOTP secret'ının düz metin saklanması, TOTP tam kilitlenmesinde kurtarma yolu, gerçek bir "davet üret" endpoint'inin eksikliği, ilk production kullanıcısının elle bootstrap edilmesi gerekliliği, M4 sonrası herkesin sıfır davetle başlaması, ve moderatör rolünün manuel SQL ile kalması — hepsi hâlâ açık.*

- 5651/KVKK compliance specifics (row 8) — not a technical control gap, a legal-verification gap. Do before real user traffic, not before v1 code.
- No independent oversight of the solo moderator (row 12) — the audit log is real, but nobody reviews it in real time while there's only one moderator. Revisit if/when a second moderator or co-founder joins.
- **No real invite-issuance endpoint (row 13):** the only way to create a production invite today is a manual `Invite` table insert via the Render Postgres console — there's no authenticated API for a user to generate one. Acceptable for a founder-issued pool at this size (`docs/BACKLOG.md`'s original framing), but doesn't scale past the founder personally handling every new invite. Concrete trigger to build a real endpoint: **M2 Slice C** (`docs/milestones/M2-core-rooms-messaging.md`), scoped and ready to implement — not just "M2, someday" anymore.
- **No in-app way to bootstrap the first production user (found 2026-07-29, row 13 follow-up):** `signup()` unconditionally requires a redeemable `Invite`, and `Invite.issuedById` is a required FK to an existing `User` — so with zero users in the database, nothing reachable through the app can create the first one. `seed.ts` can't fill this gap either: its only production-safe output is the room (`SEED_DEV_FIXTURES` gates everything else off, see above). The only working path today is fully manual: hash a password locally with the project's own `argon2` package (`node -e "require('argon2').hash(...)"`, matching `AuthService`'s plain `argon2.hash`/`argon2.verify` calls exactly, so the hash verifies correctly once inserted), then `INSERT INTO "User" (...)` directly via the Render Postgres console — no `Invite` row involved, since a bootstrap root isn't redeeming anyone's invite. Exercised for real on 2026-07-29 (founder's own production account). Concrete trigger to replace this with a real mechanism: same as row 13's missing invite-issuance endpoint — when **M2 Slice C** builds it, design it to also cover the zero-users bootstrap case (e.g. a one-time setup token or an explicit "first user" allowance), not just invite issuance for existing users.
- **Every existing user (founder included) starts at 0 invites once M4 Slice B ships (found 2026-08-05, M4 Slice C):** invites are now earned exclusively by leveling up (`InvitesService.grantInvites`, called only from `MessagesService.sendMessage` when `awardXp` reports a level increase — no other code path ever creates an `Invite` row, confirmed by reading the source). Since `User.totalXp`/`level` both default to `0`, nobody can invite anyone until they've organically sent 35 messages. **Do NOT "fix" this by manually `UPDATE`-ing `User.totalXp`/`level`** — that both violates ADR-0004 (level must always be a derivation of the real `ReputationEvent` log; a faked `level` with no backing events is an audit-trail gap) and doesn't even work (`grantInvites` only fires as a live side effect inside `sendMessage`'s transaction, so a manually-set `level` column produces zero real `Invite` rows). Correct interim procedure, same spirit as the row-35 zero-user bootstrap: generate a real, high-entropy code the same way the app does (`node -e "console.log(require('crypto').randomBytes(12).toString('base64url'))"` — never a human-chosen string, that reopens the row-9 entropy gap), then `INSERT INTO "Invite" (id, code, "createdAt", "issuedById") VALUES (gen_random_uuid(), '<generated code>', now(), '<user id>');` directly via the Render Postgres console — `id` needs the explicit `gen_random_uuid()` since Prisma's `@default(uuid())` is client-side only, not a DB default. Re-generate a fresh code on any retry; reusing one hits the `Invite_code_key` unique constraint. No permanent code path needed — this is accepted as a one-time, per-deploy manual step (`docs/milestones/M4-reputation-invites.md`'s own Risk section).
- **Moderator role assignment stays manual SQL, by design (resolved 2026-08-05, M5 scope review):** `M2-core-rooms-messaging.md` originally flagged a self-service role-management endpoint as M5 scope; re-evaluated and deliberately NOT built — M5's own Out-of-scope already rejects multi-moderator management, and for the single-moderator (founder) case, setting one's own `role` is a one-time bootstrap action, same category as the zero-user `User` bootstrap above (row 35), not a recurring operational need. `UPDATE "User" SET "role" = 'moderator' WHERE id = '<founder id>';` via the Render Postgres console. Concrete trigger to revisit: a second moderator/co-founder is ever added (which would also reopen row 12's "no independent oversight" gap above).
- `User.totpSecret` (M1 Slice B) is stored in plaintext at rest, not encrypted. **Not** the same exposure as `JWT_SECRET`/`DATABASE_URL` — those are env vars that leak only through app-server/environment compromise (Render dashboard access, shell on the running process). `totpSecret` sits in a DB row, which leaks through a distinct set of vectors that don't require touching the app server at all: a `pg_dump` backup copied or left somewhere, a future SQL-injection bug, direct Postgres console access. Deliberately deferred, not silently skipped — concrete trigger to actually encrypt it, whichever comes first: **(a)** M6 (Legal & launch readiness — already the designated hardening milestone) ships, or **(b)** real registered users exceed 50 before M6 lands. Either way, done before the public acquisition push (`docs/review/CRITIQUE.md`'s Riskiest Assumption test) goes out to strangers.
- **TOTP full-lockout recovery (M1 Slice E3):** the only recovery path built is the 8 single-use recovery codes issued at enable-time (`docs/PRD.md`'s "Zero users lost to account lockout from TOTP" goal assumes this path works). If a user loses the authenticator *and* all 8 codes, there is no code-level recovery — no admin/role concept or admin endpoint exists anywhere in the API. Interim, documented procedure: on a verified support request, the founder manually clears the lock via the Render Postgres console (`UPDATE "User" SET "totpSecret" = NULL, "totpEnabledAt" = NULL WHERE id = '<id>';`) — a manual data fix for an individual locked-out account, not a schema change. Concrete trigger to replace this with a real admin endpoint instead of a manual query: **(a)** this is requested a second time, or **(b)** M3 scope, whichever comes first.
