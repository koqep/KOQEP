# KOQEP — Threat Model

*Her satır: aktör → hedef → saldırı yolu → kontrol → kalan risk. Phase 1'in güvenlik bulgularının somut kontrollere dönüştürülmüş hali.*

| # | Actor | Goal | Attack path | Control | Residual risk |
|---|---|---|---|---|---|
| 1 | Sybil operator | Mass fake accounts to manipulate reputation/invites | Use own invite tree to farm accounts, low-effort messages to earn XP → more invites | **Revised M4 Slice B (2026-08-04):** manual invite issuance (and its explicit 5/hour-per-user rate limit, shipped M2 Slice C) was removed entirely — invites are now earned only automatically, 1 per level-up. The real ceiling today is indirect, derived from the WS message-send rate limit (10 msgs/10s, `messages.gateway.ts`) × `MESSAGE_SENT_XP=1` ÷ `XP_PER_LEVEL=35` ≈ **~100 invites/hour/user, theoretical max** — about 20x looser than the removed explicit cap. ReputationEvent log (ADR-0004) still makes farming patterns auditable | The new ceiling is real but far more permissive than the control it replaced, and reaching it requires sustained max-rate messaging (unrealistic for a genuine user, plausible for a scripted one) — a determined sybil operator has meaningfully more room than before. **Revised 2026-08-12 (500-user scope change): "small community notices" is no longer a real backstop** — at 500 users nobody has full visibility into the invite tree the way a 20-30 person group implicitly does. Residual risk is now higher than previously stated; mitigated only by the audit log (after-the-fact) and the message-rate ceiling, not by social visibility |
| 2 | External attacker | Account takeover | Credential stuffing / reused passwords; TOTP is optional so many accounts are single-factor | argon2id/bcrypt password hashing; TOTP optional but encouraged, with recovery codes at setup; refresh-token rotation/revocation. **RESOLVED (2026-08-18, M7a Slice F):** per-account brute-force lockout (`User.failedLoginCount`/`lockedUntil`, 5 wrong passwords → 15-minute lock, mirrors `mutedUntil`'s shape) closes the "no per-account slowdown" gap the global 100-req/60s-per-IP throttle left open; `PasswordPolicyService` rejects known-breached passwords at signup/password-reset via HaveIBeenPwned's k-anonymity API (plain `fetch`, no new dependency, 3s timeout, fails open on outage) | Accounts that decline TOTP remain single-factor — accepted tradeoff from Phase 1 (mandatory TOTP was a bigger risk: solo-founder lockout support burden). **Design choices made deliberately narrow, not left as silent assumptions:** only wrong PASSWORDS count toward the lockout counter, never TOTP failures (an attacker who already knows the password could otherwise grief the real owner by deliberately failing TOTP 5 times — a new, previously-impossible harm the counter would have introduced); the locked state is never distinguishable from a normal wrong-password response (a separate `ACCOUNT_LOCKED` code would let 5 arbitrary guesses against any candidate email confirm whether it's registered — a clean, IP-throttle-proof enumeration oracle, exactly the "distributed across many IPs" shape this row itself warns about) — a dummy-hash argon2 call normalizes the timing between the two paths; the lockout notification email (to the account's own address only, so an attacker never sees it) is capped to once per 12 hours per account to prevent an attacker forcing dozens of emails a day by repeatedly cycling the 15-minute lock; no password composition rules were added (NIST 800-63B treats them as friction without real entropy gain, breach-checking is the current best practice). **Known, accepted, and separately tracked gap this slice does NOT close:** `AuthService.verifyCurrentPassword` (the reauth used by `deleteAccount` and `ModeratorRoleService.assignModerator`, row 37) has no lockout — see the dedicated open item below. |
| 3 | Compromised or malicious account holder | Post benign content, edit into abuse after reputation accrues | Edit a message post-hoc once trust/level is established | MessageEdit history retained; **visible only to the message's author and to moderators** — resolved this phase, not public (avoids edit history becoming a harassment/surveillance tool). **M5 Slice B (2026-08-07):** a moderator can now apply a transparent temp-mute (`User.mutedUntil`) that blocks BOTH `sendMessage` and `editMessage` — directly closes the specific bypass this row names (mute a repeat offender's account, they can no longer edit old messages into abuse either) | Moderator response time is still bounded by a solo operator's availability — no 24/7 coverage. The mute is a reaction once abuse is noticed/reported, not prevention; a single edit-into-abuse before detection is still possible |
| 4 | Any authenticated user | XSS / content injection | Malicious markdown/HTML payload in a message | Rendered markdown passes through a sanitizing allowlist; strict CSP, no inline scripts, no remote script sources | Sanitizer or renderer library CVEs — mitigated by dependency updates, not eliminated |
| 5 | Any user or bot | Flood a room / degrade availability | Automated rapid message sending | Rate limits at the WS gateway: per-user, per-IP, per-connection — **not implemented today; planned for M2 Slice C** (a custom WS guard extending `ThrottlerGuard`) | Message sending is fully unthrottled until Slice C ships. Even once it exists, a determined actor with many accounts (ties to #1) can still degrade one room temporarily |
| 6 | Malicious user | Room-spam / squat the browse list, waste storage | Rapid, repeated room creation | Room creation capped at 1/user/24h; 14-day auto-archive removes dead rooms from the active list (ADR-0006) — **not implemented; deferred to M3**, not M2. Tied to user-created rooms, which don't exist until M3 — nothing to cap or archive today. Core rooms #general/#meta (M2) are exempt by design once they exist, not because any exemption code runs | A creation burst is still visible for up to 14 days before archiving, once M3 builds this |
| 7 | Coordinated group | Brigading — flood a room or harass a target using invite-tree access | Multiple invited accounts act in concert, controlled or coordinated by one actor | Invite-issuance control same as row 1 — **M4 Slice B (2026-08-04):** explicit rate limit replaced by the indirect, ~20x looser WS-message-derived ceiling (see row 1); reputation stays an honest signal (Boost-for-XP already killed, Phase 1); moderation is transparent temp-mute, not shadow ban, so bad actors can be muted openly and fast | Small community size means even a handful of coordinated accounts have real impact; best mitigation is a shallow invite tree and an attentive solo moderator, not technical controls alone. **Revised 2026-08-12 (500-user scope change): the "solo moderator" half of this mitigation is the actual bottleneck now — see row 12's fired trigger. Self-service second-moderator assignment shipped 2026-08-16 (M7a Slice C, row 37), restoring this row's own stated mitigation at the new scale.** |
| 8 | Regulator / legal claimant | Platform found non-compliant (KVKK/GDPR/5651) | N/A — this is a compliance gap, not an attack | Anonymize-on-delete instead of hard-delete (ADR-0005). **2026-08-21: lawyer answered the traffic-log retention DURATION question — 18 months, binding.** The codebase logs zero IP/connection metadata TODAY — this is now a legal requirement to reverse, tracked as its own milestone (`docs/milestones/M6b-traffic-log-5651.md`), not yet built | **Two SEPARATE open questions, do not conflate:** (a) traffic-log retention duration — ANSWERED (18 months), infrastructure to build tracked in M6b; (b) whether ADR-0005's anonymize-on-delete approach itself holds up under Turkey-specific case law — **the lawyer was NOT asked this, still fully open**, on the list of questions to ask next |
| 9 | Unauthenticated actor | Guess a valid invite code | Brute-force / enumeration attempts | Single-use — **implemented and tested** (`usedAt`/`usedById`). High-entropy — **not enforced by any code today**: every `Invite.code` ever created (M1's now-removed `DEV_INVITE_CODES` seed constants, and the manually-SQL'd production bootstrap invite) was a human-chosen string, not server-generated; M2 Slice C's server-side generator is the first thing that will actually guarantee entropy. Rate-limited attempts — **not implemented, planned for M2 Slice C** (retrofit `POST /auth/signup`) | Until M2 Slice C ships, an invite code's real strength depends entirely on whoever typed it when creating the row, and guessing attempts are unthrottled. Low once Slice C lands — standard token-guessing risk at that entropy level |
| 10 | Abusive account holder | Harass another user via DM, where room moderation doesn't reach | Send abusive content 1:1; no other user or moderator witnesses it | **Row written as if DM exists — it doesn't (confirmed 2026-07-30, no `Conversation`/`DirectMessage` model anywhere in the schema; re-confirmed 2026-08-12).** Previously deferred past 1.0 on the 20-30-person-closed-cohort reasoning in `docs/BACKLOG.md`'s "2026-07-30 — LANSMAN KARARI." **Status update 2026-08-12 (500-user scope review): DM is now a real, wanted feature (`docs/milestones/M8-social-features.md`) rather than out-of-scope — but still deferred past the 500-launch (M7), because it's a large lift (new data model, WS routing, ~40-60h) and the product functions without it.** When DM does ship, this row's own reasoning about report-triggered (not ambient) visibility, block/mute stopping contact immediately, and multi-report auto-flagging is the intended design — and per this same scope review, DM reporting (previously named as a real, then-deferred gap in this exact row) must ship in the SAME slice as DM itself, not as a follow-up | Requires the victim to report — a victim who doesn't report leaves no trail; pattern-detection across reports is a weak, not a strong, backstop. **DM's absence is a known, tracked gap for M8, not a moot row — 500 semi-strangers make DM-shaped harassment risk more real than the original 20-30-friends framing assumed, even while DM itself stays out of the 500-launch (M7).** |
| 11 | External attacker with a compromised email account | Take over a KOQEP account via password reset | Request password reset, receive the link via the compromised email, set a new password | If TOTP is enabled, resetting the password alone is not sufficient — TOTP is still required to log in. Reset links are single-use and short-TTL; a reset event sends a notification to the account's registered email; all active sessions/refresh tokens are revoked on password change, forcing re-auth everywhere | For accounts without TOTP (optional per Phase 1/ADR trade-off), email compromise is account compromise — the notification is after-the-fact, not preventive. This is the direct, accepted cost of making TOTP optional; stated plainly, not hidden |
| 12 | Moderator (insider) | Misuse standing access to edit history or reported content | Browse MessageEdit history or reported DM content without an actual open report/investigation reason | Moderator access to a message's edit history is scoped to an active report on that specific message/user — not a general "browse anything" query. Every moderator access and every moderation action (mute/ban) is written to its own append-only audit log (same pattern as ReputationEvent, ADR-0004): who, what, on whom, when | With a single solo moderator (the founder) at this stage, there is no independent, real-time oversight — the audit log gives after-the-fact accountability only, not prevention. Honest residual risk of a solo-operator platform, not solved by tooling alone. **Trigger fired 2026-08-12 (500-user scope change):** row 37's own concrete trigger for revisiting solo-moderator-only ("a second moderator/co-founder is ever added") is now directly implied by the 500-user target — one person cannot moderate 500 people. Self-service moderator assignment shipped 2026-08-16 (M7a Slice C, row 37). **This does not resolve the oversight gap itself (a second moderator adds capacity, not independent review of the first) — that remains open, revisit if/when real multi-moderator coordination is needed.** |
| 13 | Anyone with read access to the private repo (collaborator, leaked credential, compromised device) | Bypass invite-gating entirely; self-register on production, or log into a live account, with zero real credential | `apps/api/src/db/dev-seed.constants.ts` holds `DEV_INVITE_CODES` and `DEV_USER_EMAIL`/`DEV_USER_PASSWORD` in plaintext, committed to git; every deploy's `preDeployCommand` (`db:seed`) previously wrote both the invite codes and a real, real-password-hash dev account into the **production** database, unconditionally | `apps/api/src/db/seed.ts` now gates dev-user + invite-code creation behind an opt-in `SEED_DEV_FIXTURES` env var, default OFF (verified: `db:seed` with the var unset creates only the room, nothing account/invite-related). Production's existing dev-user row and any account signed up via a `DEV-INVITE-*` code were manually deleted from the live DB (2026-07-29) | Repo is currently private, so no external leak today — but this was the exact same risk class as the closed row 13 dev-login bypass (a "dev convenience" fixture that was a real, standing production access path). No real "issue an invite" endpoint exists yet; founder-issued invites are manual `Invite` table inserts via the Render Postgres console until one is built (M2+) — a real gap, tracked in Open items, not silently accepted |

## Open items carried forward

Oturum kalıcılığı (eskiden bu listedeydi) 2026-08-14'te M7a Slice A ile RESOLVED (satır 40). Unicode/zalgo suistimali (eskiden bu listedeydi) 2026-08-20'de M7b Slice E ile RESOLVED (satır 42). Moderasyon eylemlerinin SEBEP taşımaması (eskiden bu listedeydi) 2026-08-21'de M7b Slice D2 ile RESOLVED (satır 41) — itiraz/dispute yolu hâlâ açık.*

Kendi milestone'una taşındı (`docs/milestones/M6b-traffic-log-5651.md`) — M6 zaten kapanmış sayıldığı ve kapsam (yeni tablo + cross-cutting middleware + güvenlik-kritik proxy doğrulaması + olası depolama-planı yükseltmesi) M7b'nin "cila" niteliğinden farklı olduğu için M6'ya geri eklenmedi/M7b'ye katılmadı, ayrı bir dosya açıldı.
- **ADR-0005'in anonimleştirme yaklaşımının Türkiye içtihadıyla uyumluluğu (row 8) — HÂLÂ AÇIK, avukata henüz sorulmadı.** 2026-08-21'de avukata sadece trafik-saklama süresi soruldu (yukarıdaki madde) — anonimleştirme yaklaşımı AYRI bir soru, cevaplanmadı. `docs/milestones/M6b-traffic-log-5651.md`'nin founder-iş listesine eklendi.
- No independent oversight of the solo moderator (row 12) — the audit log is real, but nobody reviews it in real time while there's only one moderator. Revisit if/when a second moderator or co-founder joins.
- **No real invite-issuance endpoint (row 13) — RESOLVED, then OBSOLETED (found 2026-08-09, M6 scope review):** this row's own text was stale. **M2 Slice C did ship a real endpoint** (`POST /invites`, server-generated high-entropy codes) — that part of the original finding was resolved and the text simply never got updated to say so. **Then M4 Slice B removed that endpoint entirely** (`InvitesController` today only has `GET /invites` — confirmed by reading the source) as part of switching invites to auto-grant-on-level-up; manual/self-service invite issuance isn't a concept in the app anymore, so there's nothing left to "build a real endpoint" for. Not a gap — a closed row whose resolution was superseded by a later architectural decision. No action needed.
- **No in-app way to bootstrap the first production user (found 2026-07-29, row 13 follow-up):** `signup()` unconditionally requires a redeemable `Invite`, and `Invite.issuedById` is a required FK to an existing `User` — so with zero users in the database, nothing reachable through the app can create the first one. `seed.ts` can't fill this gap either: its only production-safe output is the room (`SEED_DEV_FIXTURES` gates everything else off, see above). The only working path today is fully manual: hash a password locally with the project's own `argon2` package (`node -e "require('argon2').hash(...)"`, matching `AuthService`'s plain `argon2.hash`/`argon2.verify` calls exactly, so the hash verifies correctly once inserted), then `INSERT INTO "User" (...)` directly via the Render Postgres console — no `Invite` row involved, since a bootstrap root isn't redeeming anyone's invite. Exercised for real on 2026-07-29 (founder's own production account). **Trigger update (2026-08-09, M6 scope review):** the original trigger ("when M2 Slice C builds a real invite endpoint, extend it to cover this too") is moot — M2 Slice C's endpoint was later removed entirely by M4 Slice B (see row 13 above), so there's no endpoint left to extend. Since the founder has already exercised this manual path for real on the one production database that exists, and a from-scratch "first user" endpoint has no other consumer, this is now accepted as a permanent manual procedure — same category as row 36 below. Concrete next step: fold this exact procedure into Slice F's incident runbook (`docs/milestones/M6-launch-readiness.md`) so it's not only discoverable by reading this row.
- **Every existing user (founder included) starts at 0 invites once M4 Slice B ships (found 2026-08-05, M4 Slice C):** invites are now earned exclusively by leveling up (`InvitesService.grantInvites`, called only from `MessagesService.sendMessage` when `awardXp` reports a level increase — no other code path ever creates an `Invite` row, confirmed by reading the source). Since `User.totalXp`/`level` both default to `0`, nobody can invite anyone until they've organically sent 35 messages. **Do NOT "fix" this by manually `UPDATE`-ing `User.totalXp`/`level`** — that both violates ADR-0004 (level must always be a derivation of the real `ReputationEvent` log; a faked `level` with no backing events is an audit-trail gap) and doesn't even work (`grantInvites` only fires as a live side effect inside `sendMessage`'s transaction, so a manually-set `level` column produces zero real `Invite` rows). Correct interim procedure, same spirit as the row-35 zero-user bootstrap: generate a real, high-entropy code the same way the app does (`node -e "console.log(require('crypto').randomBytes(12).toString('base64url'))"` — never a human-chosen string, that reopens the row-9 entropy gap), then `INSERT INTO "Invite" (id, code, "createdAt", "issuedById") VALUES (gen_random_uuid(), '<generated code>', now(), '<user id>');` directly via the Render Postgres console — `id` needs the explicit `gen_random_uuid()` since Prisma's `@default(uuid())` is client-side only, not a DB default. Re-generate a fresh code on any retry; reusing one hits the `Invite_code_key` unique constraint. No permanent code path needed — this is accepted as a one-time, per-deploy manual step (`docs/milestones/M4-reputation-invites.md`'s own Risk section).
- **Moderator role assignment stays manual SQL — RESOLVED (2026-08-16, M7a Slice C), with a residual risk.** `POST /moderation/users/assign-moderator` and `/revoke-moderator` both ship, reusing the existing `ModeratorGuard` pattern — any current moderator can promote or demote another, no `founder`/`admin` distinction exists in the schema. Assign requires the ACTING moderator's own password (+ TOTP if enabled) — `AuthService.deleteAccount`'s exact reauth pattern, extracted into a reusable `verifyCurrentPassword` — specifically so a hijacked session (stolen token, XSS) can't mint a durable backdoor moderator account without the real credentials. Revoke does NOT require reauth (reducing privilege is self-healing: a wrongly-revoked moderator can simply be re-promoted by anyone else). A moderator cannot revoke themselves while they're the sole remaining moderator — otherwise `ModeratorGuard` would lock both endpoints to everyone, including the founder, with no way back except manual SQL again. **What this does NOT resolve:** bootstrapping the very FIRST moderator still requires the exact same manual `UPDATE "User" SET "role" = 'moderator' WHERE id = '<user id>';` via the Render Postgres console — nobody has `role='moderator'` yet to call the endpoint, the acceptance criterion's own wording ("İkinci bir moderatör self-servis atanabiliyor") already scoped this correctly. **New risk this introduces, accepted:** any moderator (not just the founder) can now mint arbitrary new moderators — mitigated by the assign-side reauth and revoke's fast undo, not eliminated; row 12's independent-oversight gap (nobody reviews a moderator's own actions) is unchanged by this slice.
- **Moderator content removal (M5 Slice A) has no undo endpoint, by design — mistaken removals require manual SQL.** Consistent with the rest of the app: nothing supports "undo an edit" today, not even for the message's own author — Slice A doesn't introduce a new asymmetry, it just makes a moderator's mistaken removal follow the same "no built-in undo" shape self-edits already have. The original content survives in `MessageEdit.previousContent` (never hard-deleted), so recovery is possible: `UPDATE "Message" SET content = (SELECT "previousContent" FROM "MessageEdit" WHERE "messageId" = '<id>' ORDER BY "editedAt" DESC LIMIT 1) WHERE id = '<id>';` via the Render Postgres console. Concrete trigger to build a real "undo" endpoint instead: this manual fix is needed a second time.
- **`User.totpSecret` plaintext storage — RESOLVED (2026-08-12, M6 Slice E, ADR-0008):** now encrypted at rest, field-level AES-256-GCM (Node's built-in `crypto`, no new dependency). Rollout was designed to need no strict ordering between code deploy and data backfill — the decrypt path tolerates both the old plaintext format and the new encrypted format, and a separate idempotent backfill script (`apps/api/src/db/backfill-totp-secrets.ts`, runs on every deploy's `preDeployCommand`) converts existing rows. Full reasoning: `docs/decisions/ADR-0008-totp-secret-encryption.md`. **New risk this introduces, not present before:** `TOTP_ENCRYPTION_KEY` loss (both in the Render dashboard and its off-Render backup) makes every encrypted `totpSecret` row **permanently** unreadable — AES-GCM's own property, not a "hard to recover" case. Recovery codes are unaffected (stored separately, one-way hashed). Mitigation: the key is backed up outside Render (a password manager or equivalent) at generation time, not as an afterthought. **Bulk recovery procedure if the key is genuinely, permanently lost:** `UPDATE "User" SET "totpSecret" = NULL, "totpEnabledAt" = NULL WHERE "totpSecret" IS NOT NULL;` via the Render Postgres console — forces TOTP off for every affected user (same shape as row 40's single-user manual reset, just unscoped to one `id`); they re-enroll their authenticator. This is a "re-generate the secret" cost, not a permanent account lockout. No rotation path exists today either (single key, by design) — if rotation is ever needed (suspected leak, routine rotation), a second key plus a re-encryption backfill script (same shape as the current one-way backfill, reusable) would be required; not built because there's no live trigger for it, but written down here rather than left an unstated assumption (ADR-0008's own "Sonuçları" section).
- **No session-persistence mechanism — RESOLVED (2026-08-14, M7a Slice A, ADR-0002 Addendum).** `apps/web/app/page.tsx` no longer holds a fixed token pair in memory — it silently calls `/auth/refresh` on mount and on any `401` from an authenticated call, using an httpOnly refresh-token cookie the access token itself never touches. Full design (why only the refresh token moved to a cookie, the double-submit CSRF defense, the multi-tab rotation-race grace period, and a real bug the implementation's own e2e suite caught — a blanket 401-retry was silently swallowing domain errors like wrong-TOTP-code): `docs/decisions/ADR-0002-token-based-api-auth.md`'s Addendum. **New risk this introduces, accepted and time-boxed:** `AuthService.refresh()` tolerates reuse of a *rotation-revoked* refresh token for 10 seconds, exactly once (`RefreshToken.graceReusedAt`) — needed because two tabs sharing one cookie can race a rotation; narrowed by an atomic single-use claim and by never applying to logout-revoked tokens (explicit logout is always immediate). A genuinely stolen-and-replayed token gets at most one extra 10-second-window use, not indefinite reuse.
- **Moderation actions give the affected user no reason, and content removal gives no notice at all — RESOLVED for the reason/notification layer (2026-08-21, M7b Slice D2), appeal/dispute flow still open.** `MutesService.applyMute`/`ReportsService.removeContent` now require a moderator-stated `reason` (`ModerationAuditLog.reason`, `User.muteReason` for the live-state case). `MessagesGateway.notifyContentRemoved` is a new targeted, author-only WS notification (`moderation:content-removed`) — separate from the room-wide `message:updated` broadcast everyone else sees; `notifyUserMuted`'s payload now carries the reason too. **What this does NOT resolve:** there is still no way for the affected user to contest the decision — no appeal queue, no dispute UI, just a fuller explanation of what happened and why. At 500 users a single moderator's unappealable judgment is still a real fairness gap; `docs/milestones/M7b-scale-polish.md`'s founder-task line explicitly leaves open whether a real appeal flow should be pulled forward from Faz 2.
- **No Unicode/combining-character abuse protection beyond length — RESOLVED (2026-08-20, M7b Slice E).** `apps/api/src/services/content-validation.util.ts`'s `hasExcessiveCombiningMarks` (Node 22 native `Intl.Segmenter`, no new dependency) bounds combining marks to 5 per grapheme cluster — legit multilingual text (Vietnamese, Arabic harakat, Hindi vowel signs) uses 1-4/grapheme, zalgo stacks dozens/hundreds. Wired into BOTH `handleMessageSend` AND `handleMessageEdit` (`messages.gateway.ts`) — same reasoning as `assertNotMuted`'s (M5 Slice B) dual-handler coverage: checking only send would let an innocent message be edited INTO zalgo afterward, bypassing the check entirely. Rejects with `WsException({code:'MESSAGE_INVALID_CONTENT'})`.
- **Email-account-loss recovery has no real answer (found 2026-08-12, 500-user scope review).** TOTP has a built recovery path (8 single-use codes, row 40 below). Losing access to the registered email has none — password reset, the verification-email resend, and the account-deletion confirmation flow are all email-dependent, and neither a secondary recovery email nor security questions are meaningfully more secure alternatives (both have their own well-known weaknesses). Explicitly left unsolved rather than rushed: flagged here so it isn't silently forgotten, deferred to `docs/milestones/M8-social-features.md` for real design thought once there's more time than a 500-launch deadline allows.
- **TOTP full-lockout recovery (M1 Slice E3):** the only recovery path built is the 8 single-use recovery codes issued at enable-time (`docs/PRD.md`'s "Zero users lost to account lockout from TOTP" goal assumes this path works).
