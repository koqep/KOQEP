# KOQEP — Threat Model

*Her satır: aktör → hedef → saldırı yolu → kontrol → kalan risk. Phase 1'in güvenlik bulgularının somut kontrollere dönüştürülmüş hali.*

| # | Actor | Goal | Attack path | Control | Residual risk |
|---|---|---|---|---|---|
| 1 | Sybil operator | Mass fake accounts to manipulate reputation/invites | Use own invite tree to farm accounts, low-effort messages to earn XP → more invites | Per-inviter invite-issuance rate limit; ReputationEvent log (ADR-0004) makes farming patterns auditable | Slow, patient farming across weeks still possible; small community makes it more likely to be noticed by other users |
| 2 | External attacker | Account takeover | Credential stuffing / reused passwords; TOTP is optional so many accounts are single-factor | argon2id/bcrypt password hashing; TOTP optional but encouraged, with recovery codes at setup; refresh-token rotation/revocation | Accounts that decline TOTP remain single-factor — accepted tradeoff from Phase 1 (mandatory TOTP was a bigger risk: solo-founder lockout support burden) |
| 3 | Compromised or malicious account holder | Post benign content, edit into abuse after reputation accrues | Edit a message post-hoc once trust/level is established | MessageEdit history retained; **visible only to the message's author and to moderators** — resolved this phase, not public (avoids edit history becoming a harassment/surveillance tool) | Moderator response time is bounded by a solo operator's availability — no 24/7 coverage |
| 4 | Any authenticated user | XSS / content injection | Malicious markdown/HTML payload in a message | Rendered markdown passes through a sanitizing allowlist; strict CSP, no inline scripts, no remote script sources | Sanitizer or renderer library CVEs — mitigated by dependency updates, not eliminated |
| 5 | Any user or bot | Flood a room / degrade availability | Automated rapid message sending | Rate limits at the WS gateway: per-user, per-IP, per-connection | A determined actor with many accounts (ties to #1) can still degrade one room temporarily |
| 6 | Malicious user | Room-spam / squat the browse list, waste storage | Rapid, repeated room creation | Room creation capped at 1/user/24h; 14-day auto-archive removes dead rooms from the active list (ADR-0006) | A creation burst is still visible for up to 14 days before archiving |
| 7 | Coordinated group | Brigading — flood a room or harass a target using invite-tree access | Multiple invited accounts act in concert, controlled or coordinated by one actor | Invite-issuance rate limits; reputation stays an honest signal (Boost-for-XP already killed, Phase 1); moderation is transparent temp-mute, not shadow ban, so bad actors can be muted openly and fast | Small community size means even a handful of coordinated accounts have real impact; best mitigation is a shallow invite tree and an attentive solo moderator, not technical controls alone |
| 8 | Regulator / legal claimant | Platform found non-compliant (KVKK/GDPR/5651) | N/A — this is a compliance gap, not an attack | Log retention policy + documented takedown process (Phase 1); anonymize-on-delete instead of hard-delete (ADR-0005) | Turkey-specific case law on anonymization-as-erasure is not yet legally verified — flagged from ADR-0005, needs a cheap legal check before real traffic |
| 9 | Unauthenticated actor | Guess a valid invite code | Brute-force / enumeration attempts | High-entropy, single-use invite codes; rate-limited attempts | Low — standard token-guessing risk at this entropy level |
| 10 | Abusive account holder | Harass another user via DM, where room moderation doesn't reach | Send abusive content 1:1; no other user or moderator witnesses it | DMs are not proactively scanned. A report on a DM message exposes only that reported content to a moderator for review (report-triggered visibility, not ambient surveillance — same model Discord/Slack use). Block/mute stops further contact immediately, independent of any report. Additional signal: if the same account is blocked/reported by multiple distinct users within a short window, auto-flag for moderator attention | Requires the victim to report — a victim who doesn't report leaves no trail; pattern-detection across reports is a weak, not a strong, backstop |
| 11 | External attacker with a compromised email account | Take over a KOQEP account via password reset | Request password reset, receive the link via the compromised email, set a new password | If TOTP is enabled, resetting the password alone is not sufficient — TOTP is still required to log in. Reset links are single-use and short-TTL; a reset event sends a notification to the account's registered email; all active sessions/refresh tokens are revoked on password change, forcing re-auth everywhere | For accounts without TOTP (optional per Phase 1/ADR trade-off), email compromise is account compromise — the notification is after-the-fact, not preventive. This is the direct, accepted cost of making TOTP optional; stated plainly, not hidden |
| 12 | Moderator (insider) | Misuse standing access to edit history or reported content | Browse MessageEdit history or reported DM content without an actual open report/investigation reason | Moderator access to a message's edit history is scoped to an active report on that specific message/user — not a general "browse anything" query. Every moderator access and every moderation action (mute/ban) is written to its own append-only audit log (same pattern as ReputationEvent, ADR-0004): who, what, on whom, when | With a single solo moderator (the founder) at this stage, there is no independent, real-time oversight — the audit log gives after-the-fact accountability only, not prevention. Honest residual risk of a solo-operator platform, not solved by tooling alone |

## Open items carried forward
*Bu modelde çözülmeyen iki şey: TR'ye özgü hukuki doğrulama ve tek moderatörlü denetim boşluğu — ikisi de hâlâ açık.*

- 5651/KVKK compliance specifics (row 8) — not a technical control gap, a legal-verification gap. Do before real user traffic, not before v1 code.
- No independent oversight of the solo moderator (row 12) — the audit log is real, but nobody reviews it in real time while there's only one moderator. Revisit if/when a second moderator or co-founder joins.
